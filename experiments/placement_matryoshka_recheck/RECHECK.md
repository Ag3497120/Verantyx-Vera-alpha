# 事前シミュ × 再検査(配置換えマトリョーシカ) — 捏造率は下がるか

事前登録 2026-08-19。実行前に書き、実行後に数字だけを埋める。

## 出発点(記録済みの事実)

docs/PLACEMENT.md (コミット dd22760) の多腕測定:

```
                     frequency   simulated
justified ANSWER          1           3
MANUFACTURED ANSWER      21           9
correct refusal          40          52
missed                    6           4
manufacture rate      30.9%       13.2%
```

同じ測定で「マトリョーシカは全68問で単層と完全一致、寄与ゼロ」も記録
された。今回コードを読んで、その**構造的な理由**が2つ特定できた:

1. `matryoshka_consensus` のループは `while res.verdict != "ANSWER"` —
   **不一致だけを上層に渡す**。捏造は「偽の一致」なので、ANSWER を
   再検査する経路がそもそも存在しない。
2. `build_upper_shell` は競合腕を **そのままコピー** する
   (`upper.faces[dst] = dict(lower.faces[src])`)。同じデータ・同じ同点
   崩しで再実行すれば同じ結果になる。上層は文字通り下層の写しだった。

## 構想からの処方

最初の構想: 「ノードを並び替えて立体十字の傾きや位置などを調整して
探索を行なって、最後に一番安定状態でそれぞれの断面からアクセスした
結果が**一致した時に**探索終了とする」。

つまり再検査は **別の配置** から来なければならず、一致が停止条件。
写しは同じ配置なので一致が保証され、情報がゼロになる — 記録済みの
「寄与ゼロ」はこの構想に照らせば当然だった。

捏造の発生源も配置にある: frequency の同点はアルファベット順で崩され、
**配置の産物である偽の区別**が確信に化けた。ならば、core→軸の割当てを
変えて(回転・反転)もう一度探索し、**配置を変えても同じ core で ANSWER
になるものだけ**を ANSWER として残せば、配置の産物は落ち、本物
(両側面を一意に持つ core は どの配置でも勝つ)は残るはずである。

## 腕(5本)

店: clinics + shelters 2ドメイン×6core、ドメインごと12側面から各core
無作為8個(seed固定)。質問は「what has X Y」(側面2つ)、需要は zipf
(ドメインごと sha256 による恣意安定順、重み1/rank)。train(seed 100-102)
が simulated の需要モデルに入り、test(seed 999、train と重複除去) を
測る。**dd22760 の台本は committed されていないので、これは記述からの
再構成 — 30.9/13.2 の再現ではなく、同一 run 内の腕どうしの比較が主張**。

1. frequency 単層 (基準線)
2. simulated 単層 (基準線)
3. simulated + マトリョーシカ写し (carry=A, 3層) — 複製対照。
4. simulated + 再検査1回: 2回目は core→軸割当てを1つ回転して再探索。
   両方 ANSWER かつ同じ core のときだけ ANSWER。それ以外は
   AMBIGUOUS_ARRANGEMENT に降格。
5. simulated + 再検査2回(回転+反転): 3配置すべて一致でのみ ANSWER。

判定鍵: 質問の2側面を両方持つ候補 core がちょうど1つのとき、その core
を名指す ANSWER だけが justified。それ以外の ANSWER は捏造。

## 事前予測

- H1: 腕3 = 腕2 と全問一致(複製の確認)。
- H2: 腕4 は同 run の腕2 より捏造 ANSWER が減る。正当 ANSWER の大半は
  残る(一意保持 core は配置不変で勝つはず)。
- H3(コスト、正直に記録): 再検査は ANSWER を作れず降格しかできない。
  正当 ANSWER が配置依存だった場合はそれも落ち、missed が増え得る。
  4セル全部を報告する。
- H4: 腕5 は腕4 と同等以下の捏造率。追加の検査が正当まで削り始めたら
  そこが再検査回数の上限。

## 停止条件

腕4 の捏造率が腕2 を上回ったら、この接続は否定されたと記録して止める。
数字の書き換え・腕の追加はしない。

## 追記(第1回実行後、2026-08-19)

第1回(n_test=29): H1確認(写しは全問一致)。しかし腕4/5の軸配置換えは
唯一の捏造 ANSWER を落とせなかった — 探索自体が腕交換・回転を持つので
**軸割当てには既に頑健**であり、捏造の発生源は軸ではなかった。

docs の機構説明を読み直すと発生源は **配置の同点崩し** にある:
`score_facets` は同点を facet 昇順(アルファベット順)で崩す
(`out.sort(key=(-score, facet))`)。偽の区別はここで生まれる。よって
再検査で換えるべき配置は軸ではなく **同点の崩し方** — 同点を降順で
崩した第2の配置でも同じ core で ANSWER になるものだけを残す。

修正腕(実行前に登録):
- 腕6 recheck_ties: simulated の picks を同点降順で作り直して再探索、
  一致のみ ANSWER。
- 腕7 recheck_ties_freq(探索的・機構確認用): frequency にも同じ門。
  捏造=同点artifact 説が正しければ frequency の捏造こそ大きく落ちる。

test も n≈68 目標に増やす(zipf 重複除去後の実数を報告)。腕1〜5は
そのまま再実行して並記する。停止条件は変更なし。

## 結果(2026-08-19、n_test=62、seed全固定、results_recheck.json)

```
                      justified  manufactured  correct_refusal  missed  捏造率(全問中)
frequency                 2          9              41            10      14.5%
simulated                 1          4              46            11       6.5%
matryoshka写し(腕3)        1          4              46            11       6.5%   ← 全問一致 (H1確認)
軸換え再検査1回(腕4)        1          4              46            11       6.5%   ← 効果なし
軸換え再検査2回(腕5)        1          4              46            11       6.5%   ← 効果なし
同点換え再検査(腕6)         1          0              50            11       0.0%   ← H2確認
同点換え再検査 freq(腕7)    0          0              50            12       0.0%   ← 正当も落ちた
```

## 判定

- **H1 確認**: マトリョーシカ写しは全問一致。構造的理由も特定済み —
  ループが不一致しか上層に渡さず(捏造=偽の一致は検査対象外)、上層は
  下層のコピー。
- **H2 確認、ただし配置の階層が違った**: 捏造の発生源は軸割当てでは
  なく **placement の同点崩し**(`score_facets` の facet昇順)。同点を
  逆向きに崩した第2の配置で再探索し一致した ANSWER だけを残すと、
  simulated の捏造 4→0、**正当 1 は無傷**、正しい保留 46→50。
- **H3(コスト)**: simulated 側はコストゼロ(missed 11→11)。frequency
  側(腕7)は捏造 9→0 と引き換えに正当 2→0 — frequency の「正当」も
  同点運だったことの暴露。**事前シミュあっての再検査**: シミュが本物を
  配置不変にし、再検査が配置依存だけを落とす。組み合わせが本体。
- **H4**: 軸レベルの再検査は0回で十分(探索が既に軸頑健)。同点レベルは
  1回で捏造ゼロに到達。この店ではそれ以上の再検査は不要。

## 答え(ユーザの問いへ)

「事前シミュ×マトリョーシカの再検査で捏造率は減るか」— **減る。ただし
上層が写しである限りは1問も減らない(実測済み・構造的必然)。減るのは
再検査が別の配置(同点の崩し方)から来て、一致を停止条件にしたとき**。
これは最初の構想の「複数の断面からアクセスした結果が一致した時に探索
終了」そのもので、写しマトリョーシカはその構想の実装になっていなかった。

## 追記2(実ストア測定の事前登録、2026-08-19)

前セッションの記録(ユーザ提供)と照合した。前セッションも同じ進行
(30.9→13.2→7.4%)の後に同じ3点実装(配置摂動・既定オフの不変性ゲート・
fork固定)を提案し、「実storeでの確認」で止まっていた。昨日の合成店
測定はその独立追試に当たる。残るは実ストアのみ。

設計:
- 店: vera-corpus/build/vera.db の ja ソブリン(89,369核)。読み取り専用。
- 探針: resolution.calibrate で確立済みの形 — facet を8個以上持つ核から
  決定論的に300個抽出し、中頻度の facet 3語で問う。正解=出所の核。
  需要(train)は同じ母集団から別seedで3反復(derive_split と同じ論法)。
- 経路: candidates_for_query(k=6) → choose_for_core(frequency/simulated)
  で殻を組む → run_consensus。
- 門: 同点を逆順で崩した第2配置で再探索、(verdict, core) 一致のみ
  ANSWER 維持、不一致は AMBIGUOUS_PLACEMENT に降格。
- 指標: 正答 ANSWER / 誤答 ANSWER(実ストアでの捏造相当=自信を持って
  違う核を名指す) / 拒否。門が降格させた ANSWER の内訳(誤答何件・
  正答何件)=門の精度。

事前予測:
- H5: 降格された ANSWER のうち誤答が過半(門の精度>50%)。
- H6: 誤答率の低下幅 > 正答率の低下幅。
停止条件: 門が正答を誤答より多く降格したら、実ストアでは否定と記録
して止める。その場合エンジン本線への配線はしない。

## 実ストアの結果(2026-08-19、results_recheck_real.json)

vera.db ja(89,369核)、中頻度facet3語×300探針(正解核を植え込み):

```
                     correct  wrong  refusal   門の降格(正答/誤答)
frequency  単層          0     268     32
simulated  単層          2     278     20
simulated + 門           2     275     23        0 / 3
frequency + 門           0     267     33        0 / 1
```

- **H5 確認**: 降格4件は全て誤答(精度100%)。正答は1件も落ちない。
- **H6 確認**: 誤答のみ減少、正答は不変。停止条件は非発動。
- 正直な注記2つ: (1) reachable 27/300 — 「wrong」の大半は検索の未決定
  性(3語では核が候補6件に入らない)で、捏造とは別物。この測定が証明する
  のは門の**安全性**であって大効果ではない。(2) 実ストアでは同点自体が
  稀(実データは質量差を持つ)なので、門の発火は 4/546 ANSWER(~0.7%)。
  安価な保険であり、合成店(全カウント同一=最大限に同点)は効果を過大に
  見せていた。

## 配線について — 実装は既に存在していた

測定後にコードを精査した結果、前セッションが提案した3点は**既に本体に
実装済み**だった: `consensus_over_store(placement_invariant=)`(既定
オフ)、`build_shell_from_store(tie="desc")`(同点の走り内だけを逆順 —
本実験の粗い全逆順より正確)、fork `PLACEMENT_INVARIANCE`、さらに
engine.py の observe 経路への配線まで。前セッションはこれを入れた上で
「実storeでの確認が要る」と止まっていた — 本実験がその確認に当たる。
docstring に実ストアの数字を補記した(consensus_store.py)。

`build_upper_shell`(マトリョーシカ上層)の同点換えへの差し替えは
**行わない**: 上層は placement 文脈(store/score)を持たない API であり、
未測定の外科手術になる。測定済みの門(2回引いて一致のみ ANSWER)が同じ
性質をエンジン側で既に提供している。
