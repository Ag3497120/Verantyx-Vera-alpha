# 事前登録2: 巡回の残り扉 — CLI の ask が同じ構造の回され方を引き継ぐ

日付: 2026-09-01。**この文書を書き終えてから測定を走らせる。**

## 発端

PREREG.md の配線で巡回は MCP の会話扉(vera_chat)と engine の主席に
届いたが、CLI の `vera ask`(cmd_ask → _route → consensus_over_store)は
circulation を渡していない — 同じ器官に、扉によって届いたり届かなかったり
する状態。PREREG7(CLI parity)の線「扉は一つ、入口は二つ」に反する。

## 設計(読み書きの規則)

- CLI は `<store>.circulation.json`(会話扉が既に使っている側車ファイル)
  を**在るときだけ**読む。無ければ作らない — 一発の ask が黙って
  状態ファイルを増やすのは、扉の副作用を増やす方向で、既定の純粋さを守る
- 在るとき: 種として渡し、ANSWER の終端配置を同じ鍵規則
  (core_key・locks は合流)で書き戻して保存する
- 巡回は配置のみ。答えを変える権限を持たない(fork 契約は既に固定済み)

## 測定(M3 — 実 CLI サブプロセスで。治具は測るものと同じ経路)

1. 側車ファイル**なし**: `vera ask` を2回 → 応答がバイト単位で従来と
   同一、側車ファイルが**作られない**こと
2. 側車ファイル**あり**(会話扉が書く形をそのまま置く): `vera ask` が
   seeded_from を名乗り、verdict・core・text は側車なしと同一のこと
3. ANSWER 後に側車の当該核へ終端配置が書き戻されていること

## 採択基準

- J1: 測定1(無側車の純粋さ)が成立 — 破れたら配線を戻す
- J2: 測定2(到達と無害)が成立 — text が1件でも動いたら停止
- J3: fork 91本 + 測定が基線(Linux: 31/34、落ち5本は環境依存で不変)
  と一致
